# 04. Profiling & Validation Specification

## Objective
Phase 2 validates the raw landing data generated by the extraction phase without silently fixing underlying source integrity issues. The purpose is to identify and quarantine invalid or anomalous records while preserving the original operational evidence for downstream stages. Validation is intentionally strict: bad rows are logged and segregated, not deleted without an audit trail.

## Input / Output Paths
### Inputs
- `data/raw/raw_inbox.csv`
- `data/raw/raw_directory.csv`
- `data/raw/raw_api.json`

### Outputs
- `data/validated/validated_inbox.csv`
- `data/validated/validated_directory.csv`
- `data/validated/validated_api.json`
- `data/quarantine/api_errors.json`
- `data/quarantine/directory_duplicates.json`
- `data/quarantine/inbox_duplicates.json`

## Validation Rules
1. Critical null checks run immediately after the raw files are loaded. Rows missing required fields are not silently fixed or filled in place. They are removed from the downstream validated pipeline and quarantined for manual review.
2. Inbox records are quarantined when `Message_ID`, `Sender_Email`, or `Timestamp_IST` are null/blank. These rows are written to `data/quarantine/critical_nulls.csv` with their source and missing-field metadata, and the count is logged explicitly.
3. Directory records are quarantined when `student_id` is null/blank, since this key is required for identity resolution and downstream joins.
4. API payloads are quarantined when `interaction_id` is null/blank, and the offending records are explicitly counted and preserved in the quarantine audit trail.

## Validated Anomaly Rules
1. API network errors are quarantined when they match raw HTTP error envelopes such as `500 Internal Server Error` or `504 Gateway Timeout`. Valid records are retained in the validated API dataset.
2. Duplicate directory records are identified by repeated `student_id` values. The first occurrence is retained for the validated directory, and all duplicates are written to quarantine.
3. Inbox duplicates are detected on exact `Message_ID` + `Timestamp_IST` + `Body` combinations. Matching rows are logged and quarantined instead of silently removed.
4. `Timestamp_IST` is parsed strictly to datetime objects. A new `Is_Batch_Spike` flag is created when more than 50 rows share the same exact second, and `Is_Off_Hours` marks timestamps between 2 AM and 5 AM.
5. Inbox records are merged against the cleaned directory on `Sender_Email`. Missing matches are retained and stamped as `Unknown Identity` rather than dropped.
6. `Missing_Attachment_Anomaly` is set to True when the body contains attachment-related language (attach, receipt, document) but the message is marked `Has_Attachment = False`.

## FDE Assumptions & Limitations
- We assumed missing identities should be retained and flagged as `Unknown Identity` to measure full operational burden, rather than dropping them.
- Parsing malformed text amounts (e.g., `50 00`) is deferred to the Phase 3 analytical modeling stage to preserve the raw text integrity in the validated layer.
- Validation does not silently normalize or drop records. Whenever a rule triggers, the offending data is logged or quarantined so downstream teams can review the exact scope of the anomaly.
- This phase intentionally focuses on explicit anomaly detection and auditability rather than data repair, which is reserved for later pipeline stages.
